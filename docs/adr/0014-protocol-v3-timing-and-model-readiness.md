# ADR 0014: Protocol v3 — model-readiness metadata and the timing contract

## Status
Accepted (M3bis, 25 October 2026) for the wire contract, parsers, and transport serialization, validated by synthetic checks only. Measurement producers (RAG/Gateway/first-visible) and card display remain M04/M05; detector execution remains M07. No live latency, account-access, quality, or native result is claimed here.

## Context
The revised implementation brief and plan contracts C07/C08 require two things the recorded v2 payload cannot express:

1. **Role and capability readiness.** An answer and a detector proposal need different model capabilities (text in/out, image input for an explicit screenshot, structured output for proposals). v2 carries only a `model` string on `answer_accepted`/`answer_finished`, so nothing records which role was validated, which model was effective, where that choice came from, whether a deprecated alias was substituted, whether low reasoning was actually sent, or how certain any of it is.
2. **Timing with defined clocks.** v2 carries a single `latencyMs` on `answer_finished`. It does not say what it measures, which clock it uses, or which stages (acceptance, RAG, Gateway start, first nonempty delta, display, completion) exist. C08 forbids mixing client and backend timestamps, substituting zero for a missing measurement, or reviving a terminal record with a late timing update.

`AGENTS.md` and plan task M3bis-T03 require a protocol version bump when the wire contract changes, while preserving the recorded v2 contract and the legacy manual adapter.

## Decision
- **Version bump, additive contract.** `protocolVersion: 3` is added. The server accepts v2 and v3 (`SUPPORTED_WIRE_VERSIONS = (2, 3)`), negotiates the highest common version during `hello` (`supportedProtocolVersions` may be advertised by the client; the chosen version is returned in `hello_ack` and used in every later envelope for that connection). A version this build does not support is rejected with `incompatible_version`, and the error names the supported list. A v2 client keeps receiving the exact recorded v2 payloads; v3-only members are omitted for it. A recorded v2 payload is never reinterpreted as v3 (`contracts/v2/` fixtures are unchanged; `contracts/v3/invalid_v2_payload_at_v3.json` documents the strictness).
- **Capabilities.** v3 advertises `model_readiness` and `timing` in addition to `assist` and `snapshots`. `candidates`, `answer_records`, and `full_auto` remain unadvertised until their milestones pass.
- **Model readiness (roles).** Two roles exist: `answer` and `detector`. A static, dated registry (`backend/app/model_roles.py`) holds public-catalog facts for the two models this build actually defaults to; everything else is `certainty: "unknown"`. `imageInput` and `structuredOutput` are reported `true` only when positively known, so an attachment-bearing or detector request that needs an unverified capability fails visibly with `unsupported_capability` instead of dropping the image or guessing. When this backend has actually read the Gateway language catalog and the selection is absent from it, the request is rejected with `unavailable_model`; with no catalog read, the model is `unknown`, not unavailable. A deprecated alias is recorded as `selection_source: "deprecated_alias"` with `substituted_from` and a notice, so a substitution is visible rather than silent. Reasoning is applied (and reported `applied: true`) only for the verified Flash default; another model's accepted effort is recorded but not sent. Preflight runs before the snapshot is consumed and before any paid call, so a rejected request keeps its target.
- **Timing (C08).** Two clock domains are kept apart and never subtracted from each other:
  - Backend values are milliseconds **relative to request acceptance** on the server monotonic clock (`clock: "server_monotonic"`, `acceptedMs: 0`). Stages: `rag {startMs, endMs, durationMs, outcome}`, `generation {startMs, firstDeltaMs, endMs, durationMs}` (`firstDeltaMs` = first nonempty answer-content delta, reasoning/heartbeat/usage-only frames excluded), and `completedMs`.
  - `unavailable` names every stage the backend did not produce. A missing value is `null` and is never replaced with `0` or a benchmark TTFT.
  - The client's press instant may be sent as `clientPressedAtMs` and is **echoed only** (`timing.client.pressedMs`). The backend never computes a duration from it.
  - `firstVisibleMs` and `terminalReceivedMs` are client-only checkpoints. The server always emits `null` for them. Press-to-visible is derived on the client from two client values, and receiving a socket event does not count as display.
- **Event placement.** A new scoped `answer_timing` event carries cumulative backend timing with its own monotonic `timingSeq` (independent of content `eventSeq`, so timing never displaces or duplicates answer content). It is emitted at acceptance and may be emitted again as stages complete. `answer_finished.timing` is the authoritative final object; like final text, later timing events cannot rewrite it. Timing events follow the same owner/request/answer/snapshot/epoch scoping as content and cannot revive a terminal record.
- **Frozen metadata.** `answer_accepted.frozenInputs` (v3) adds `mode`, `presetId`, `model` (role, effective model, requested model, selection source, reasoning, capabilities, certainty, substitution, notice) and `screenshot` (`requested`, `included`, `reason`). `answer_finished` adds `modelSettings` and `timing`. A rerun re-freezes all of it.
- **Error codes.** `unsupported_capability` (known-incompatible or unconfirmed capability for the role/attachment) and `unavailable_model` (absent from a catalog this backend read) are added. Existing codes are unchanged.

## Alternatives considered
- **Reuse `latencyMs` and document it better:** rejected — one number cannot separate acceptance, retrieval, Gateway start, first delta, and completion, and cannot express a missing measurement honestly.
- **Carry timing only in `answer_finished`:** rejected — an early `answer_timing` lets M04/M05 request details show progress and gives the reducer a scoped update path that cannot disturb content ordering.
- **Put timings in the free-form `metadata` object:** rejected — unvalidated, unversioned, and easy to fabricate; the parser could not enforce clock labels or ordering.
- **Change v2 in place:** rejected — `AGENTS.md`/M3bis-T03 require a version bump, and in-place change would reinterpret already-recorded fixtures and clients.
- **Reject unknown models outright:** rejected — it would break existing saved/environment selections. Unknown models stay usable for text-only answers with an explicit unverified notice.
- **Silently substitute a deprecated alias (status quo):** rejected for the contract — the substitution is now recorded and visible, while the compatibility mapping itself is unchanged.

## Consequences
- New/changed paths: `backend/app/cockpit_models.py` (v3 models/enums/error codes), `backend/app/model_roles.py` (new), `backend/app/cockpit_protocol.py` (v3 parsing: model settings, backend/client timing, `answer_accepted`, `answer_timing`), `backend/app/assistance.py` (v3 capabilities, negotiation, request-record metadata/timing), `backend/app/ws_server.py` (`ConnectionInfo.protocol_version`), `backend/app/main.py` (negotiation, preflight, frozen inputs, timing serialization), `frontend/src/cockpit/types.ts`, `frontend/src/cockpit/protocol.ts`, `frontend/src/cockpit/reducer.ts`, `frontend/src/ws.ts`, and the new `contracts/v3/` fixtures parsed by both harnesses.
- `backend/app/main.py` currently measures only the acceptance and terminal anchors. RAG, Gateway, first-delta and first-visible producers are M04/M05; until then those stages are `null` and listed in `unavailable`. Advertising `timing` is honest because the field set and nullability are implemented, not because every stage is measured.
- Preflight is runtime policy and applies to v2 requests too; a v2 client gets the same `unsupported_capability`/`unavailable_model` rejection but not the v3 reporting block.
- The detector role is specified and unit-tested for capability rules only; no detector runs and no `candidates` capability is advertised.
- `docs/API.md` gains a "Protocol v3" contract section; ADR 0012 remains the v2/ownership/lifecycle authority and is amended, not replaced.
- No persistence keys, RAG storage, benchmark data, or Settings workflow changes.
